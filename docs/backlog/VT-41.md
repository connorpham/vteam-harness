# VT-41: three dependabot PRs that could never go green separately — one CodeQL version, three PRs
- status: In Review
- labels: supply-chain, ci
- estimate: 0.25d
- type: Task

**30-second summary:** dependabot opened one PR per action path for the same `github/codeql-action`
bump. `init` and `analyze` must run on the same version, so #69 (init) and #70 (analyze) were RED
by construction — each one alone creates a mismatch — while #71 (upload-sarif, a separate workflow)
was green. All three sat unmerged for three weeks with the pins stale. This lands the one version
across all three usages in a single change, and groups the family in `dependabot.yml` so the next
bump arrives as one PR.

## Why
An unmergeable dependency PR is worse than none: it trains the owner to ignore the red, and the
pins stay stale meanwhile — three weeks here, on the one supply chain this package has (it ships
zero runtime dependencies, so the CI actions are the whole attack surface). Spec: `.github/dependabot.yml`,
`.github/workflows/{codeql,scorecard}.yml`. no UI.

## Acceptance criteria
- Given the three usages of `github/codeql-action` / When this lands / Then all three carry the same SHA, verified against the upstream repository rather than trusted from the PR body.
- Given a future bump of the same family / When dependabot runs / Then it opens ONE grouped PR, not one per path.
- Given the combined change / When CI runs / Then every check is green, including the two that were red on #69 and #70.

## Out of scope
Moving off SHA pins to tags (a pin is deliberate — a tag is mutable); auto-merging dependabot PRs.
