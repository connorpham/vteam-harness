# VT-29: docs_shrink_check turns a full CI clone shallow — graph_check then reads the PR base tip as a root commit
- status: In Review
- labels: gate, ci, bug
- estimate: 0.25d
- type: Bug

**30-second summary:** on `pull_request` runs the first gate step fetched the base branch with
`git fetch --depth=1`. A depth-limited fetch into a full clone writes `.git/shallow` with the base
tip as a boundary; from then on `git show <base tip>` diffs against the empty tree. Six steps later
`graph_check`'s CODE-SCOPE rule saw the VT-26 commit "touching" all 501 files and went RED on
PR #75 — deterministically, while the `push` run of the same commit was GREEN. PR #74 passed only
because its base tip (a merge commit on main) is attributed to no ticket.

## Why
A gate whose first step corrupts the repository for its later steps is a false-RED generator on
exactly the branch pattern the doctrine prescribes (stacked ticket branches). Found while
publishing VT-27; reproduced locally by fetching the PR merge ref the way actions/checkout does
and running the step: `.git/shallow` = a82e8748, `git show` 12 → 501 files, graph RED. Spec:
core/scripts/docs_shrink_check.sh header; no UI.

## Acceptance criteria
- Given a full clone with a remote / When `docs_shrink_check.sh` runs with `GITHUB_BASE_REF` set / Then the comparison still runs against the base branch and `.git/shallow` does not appear.
- Given the selftest / When run against the pre-fix script / Then it is RED naming the shallow file; after the fix, GREEN.
- Given the faithful PR-clone reproduction / When the fixed step runs / Then `git show` of the base tip still lists its 12 files and graph_check is coherent.

## Out of scope
Hardening graph_check against shallow clones a user's own CI creates on purpose (fetch-depth 1) — a separate decision about whether the CODE-SCOPE rule should skip loudly there.
