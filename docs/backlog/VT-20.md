# VT-20: end-to-end review of the flow — three skills the lane could never reach, and a tool measuring with two of six tokens

- status: In Review
- assignee: Connor Pham
- estimate: 0.5d
- labels: doctrine, workflows, gates, audit, from-field-trial

## Why

An end-to-end review of the whole flow — every workflow, every gate, every competency, and the
chain between them — asked two questions: is anything duplicated or contradictory, and would an
agent actually do what the doctrine says. It found seven things, four of them live defects. None
was found by a gate; every existing check verified a *file* and none verified the *chain*.

## What was broken

**1. Three competencies the lane could never read.** `/ba` and `/pm` contained the word
"competency" **zero times**. `ba-acceptance-criteria`, `ba-story-slicing` and `pm-prioritisation`
are all declared `applies: always` — load on every session of that lane — and were written, gated,
indexed and deployed without one line ever reaching the lane that needed them. Reachability was
**28/31**. That includes the falsification question added in VT-15: it changed two criteria when
this ticket's author applied it by hand, and `/ba` would never have supplied it.

**2. The measurement tool implemented four of six token kinds.** `route_check` handled `always`,
`label:`, `term:` and `type:`, and silently ignored `profile:` and `path:`. A second bug read
`stack.profile` from the repo the script ran *from* rather than the repo being measured. Every
figure VT-16 and VT-19 published was a floor: the nine field tickets load **102 → 98 files**, not
84 → 81, and VT-19's saving is **−4.2%**, not −3.8%. The tell was a competency that had "never
loaded" across nine tickets — `dev-stack-nextjs-prisma`, whose only token is `profile:`, in a repo
whose profile is exactly that.

**3. A shipped doctrine change broke a consumer's gate.** VT-19 regenerated the INDEX with
`--write-index`, which writes `{paths.team}` — the **deployed mirror**. In the framework repo that
can never reach `core/doctrine`, the copy that actually ships. Reproduced: a consuming repo ran
`vteam update`, received the fresh competency file and the stale INDEX, and its gate went **RED**
through no fault of its own.

**4. `/qa` V2 enumerated the `always` rows by hand and had drifted both ways** — naming
`qa-user-mindset` and `qa-security-probes`, which are no longer `always` (D8/D9), and missing
`qa-identity`, `qa-report-writing` and `qa-requirement-smells`, which are. Two are rescued by V1's
prose; `qa-report-writing` is named nowhere else in the lane. The sentence also contradicted the
INDEX's own header, which says an `always` row loads at the step its `Loads at` column names.

**5. One genuinely duplicated rule.** Of 225 rules across 31 files, **zero** titles repeat
verbatim and one pair says the same thing in two files that are **both `always` for QA** —
`qa-identity` and `qa-report-writing` each carried "every claim has an evidence file behind it",
with near-identical *Otherwise* clauses. Every QA session paid for it twice. (A second near-pair,
`qa-test-design` and `qa-user-mindset` on the real-user move, is **not** duplication: the always
file states the rule short and cites the routed file, which carries the 13-item depth. That is
progressive disclosure working.)

## What was fixed

- `/ba` B2 and `/pm` P1 now load their competencies, in `/dev` T2's shape. Reachability **31/31**.
- `/qa` V2 reads the `always` rows off the index instead of a memorised list, and respects the
  `Loads at` column, which removes the contradiction with the INDEX header.
- `route_check` implements `profile:` and `path:`, and reads the profile from the repo whose
  backlog it measures. VT-16's and VT-19's evidence and the 0.18.0 changelog carry corrections
  rather than being quietly edited.
- The source INDEX was regenerated, and a `doctrine-source` gate step now checks it — guarded by
  `requires: core/doctrine/competencies`, so consumer repos skip it by declaration.
- `competency_check` now validates the **chain**, not only the file: a lane whose workflow never
  mentions competencies is an error, and a `loads` value that names no step in that lane's
  workflow is an error. Proven by reverting `/ba` and watching it red.
- `qa-report-writing`'s duplicate rule became the part only it owns: name the file beside the
  claim. The backing rule stays in `qa-identity`, which loads first.

## Found and NOT fixed — they need a decision or a bigger change

- **`/plan` and `/pm` share the `P` prefix with different meanings at every number** (P1 is "THE
  BRIEF" in one and "PICK THE WORK" in the other). Filed as **D15**; renaming a lane's step
  vocabulary touches every doc that cites it.
- **`/pm` has no P3.** P0, P1, P2, P4 — a hole in the numbering, with no trace in git of a removed
  step. Cosmetic until someone writes `loads: P3`.
- **`/ba`, `/pm` and `/docs` never consult `Reviewer lens`** — a section `competency_check`
  *requires* in all 31 files. In those three lanes it is written, gated and unread. `/dev` and
  `/qa` use it twice each.
- **Three checkers that call themselves machine gates run in no gate**: `evd_ui_check.py` (5
  mentions in `/dev`), `schedule_check.py` (2 in `/pm`), and `review_check.py` — which *is*
  enforced, but only by `.githooks/pre-push.new`, the packaged hook this repo does not use. So
  **D11 is not a cosmetic divergence: it disables a rule the dev lane states four times.**

## Acceptance criteria (testable)

1. `grep -ci competenc core/workflows/ba.md` and the same for `pm.md` both return > 0; the reach
   audit returns **31/31**.
2. Reverting either workflow makes `competency_check` red with the "never mentions competencies"
   error; a `loads` value naming a non-existent step reds too.
3. `route_check --json` on the field backlog reports `profile:` matches on 9/9 tickets, and the
   corrected totals (98 files / 108,365 tokens) are reproducible.
4. A consumer repo that runs `vteam update` gets a **green** `competency_check`; `gate.sh` in the
   framework repo runs a `doctrine-source` step and a consumer repo skips it by declaration.
5. No rule title appears in two competencies that are both `always` for the same role.
