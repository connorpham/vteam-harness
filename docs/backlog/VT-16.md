# VT-16: make routing visible — `route_check`, and the two questions it exposes

- status: In Review
- assignee: Connor Pham
- estimate: 0.5d
- labels: doctrine, competencies, context, routing, tooling, from-field-trial

## Why

The owner's original complaint about this framework was that a lane runs out of context on
a full task. VT-14 attacked that with progressive disclosure and moved 2,459 words off the
`always` path — and measured **−0.2%** on the DEV floor, because the catalogue grew by as
much as the `always` set shrank. That result said the `always` set was the wrong place to
look. This ticket finds where the cost actually is.

`competency_check` validates the `applies:` **grammar** — a token must be
`always | label:x | path:x | profile:x | term:x`. Nothing has ever checked those tokens
against a real ticket, so two faults were invisible: a ticket that needs a competency and
matches no token (**under-routing**), and a competency dragged in by a common word
appearing incidentally in a ticket's prose (**over-routing**). The second is what fills a
lane's context.

Measured across the field trial's nine tickets (`evd/VT-16/dev/routing-cost.md`):

| lane | competency files per ticket | ≈ tokens of competency text |
|---|---|---|
| dev | 5 – 15 | 4,179 – **17,270** |
| qa | 9 – 11 | 8,912 – 11,433 |

The worst case, TB-4, opens **fifteen** competency files. Five of them are pulled in by a
word that appears **only** in the ticket's prose — never in its title, labels, summary or
acceptance criteria. Two unambiguous examples, both on TB-6, a ticket about a CSS focus
ring: `dev-mobile-craft` loaded because the word "permission" appears somewhere in the
body, and `dev-query-performance` because "pagination" does. TB-3 loaded `dev-async-work`
on the word "worker", which in that ticket is "Orca worker" — an agent, not a background
job.

## What was tried and rejected, with the numbers

The obvious fix — match `term:` only against title + labels + summary — cuts **17%**
overall and **38–42%** on the worst DEV tickets. It is still wrong, and the same script
shows why: it drops 3 false matches and **12 true ones**. TB-7 and TB-9 lose
`dev-debugging` although both are `type: Bug`; TB-3 and TB-4 lose `dev-api-design`
although both add a real endpoint; three tickets lose `qa-security-probes`, which the
`/qa` workflow explicitly wants on any auth/roles ticket. Recorded here because the
tempting version of this ticket ships that change.

The diagnosis is not the *scope* of the match. It is that several `term:` tokens are
single common English words — `bug`, `model`, `lock`, `worker`, `permission`,
`pagination`, `alert`, `sync` — which appear incidentally in any long ticket.

## Acceptance criteria (testable)

1. **Given** any repo with competencies and a backlog, **When** `route_check.py` runs,
   **Then** it prints, per ticket per lane: the `always` set, every routed competency with
   the token that pulled it in **and where that token was found**, and the file count and
   word/token cost of the whole set.
2. **Given** a competency matched only by a word in the prose, **When** the report is read,
   **Then** that row is flagged `body-only` and the summary counts how many pairs have one
   — and the output says in words that this is a signal, not a verdict.
3. **Given** `--ticket <KEY>`, `--role <lane>`, `--weak` and `--json`, **When** each runs,
   **Then** the output narrows as documented and `--json` is valid JSON.
4. **Given** the default invocation, **When** it finds body-only matches, **Then** it still
   **exits 0**: it is a report, because what counts as over-routing is a decision the owner
   has not made. Only `--strict` exits 1.
5. The measured routing cost of the field trial's nine tickets, and the rejected narrowing
   experiment with the list of true matches it would have dropped, are committed as
   evidence rather than described.

## Out of scope, and why

- **Changing any `applies:` line.** Two candidate fixes need a decision first, filed as
  D13: (a) extend the grammar with a `type:` token so `dev-debugging` routes on a ticket's
  `type: Bug` field instead of the word "bug" — the structural truth the ticket already
  states, which no current token kind can express; (b) require a `term:` to appear in a
  structural field, or twice, before it counts. Both change a contract every competency
  depends on.
- **Making this a gate.** It becomes gateable once (a)/(b) are decided; until then a gate
  would fail runs over a judgement nobody has made.
