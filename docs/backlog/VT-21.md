# VT-21: close the limitations the end-to-end review left open

- status: In Review
- assignee: Connor Pham
- estimate: 0.5d
- labels: gates, workflows, doctrine, from-audit

## Why

VT-20 reviewed the flow and left four limitations it deliberately did not fix. This closes them,
and one of the four turned out to need a new idea rather than a new step.

## What changed

**1. Two checkers that called themselves machine gates now run in a gate — but not the same way,
because they are not the same kind of check.**

`evd_ui_check` is about the change being gated, so it is **hard**. It gained `--sweep` (the shape
VT-17 proved), with the same legacy policy: a pack that never adopted the `NN_<description>.png`
layout is **reported, not failed** — the field repo's TB-8 has 106 images in subfolders and has
never been judged by this checker, which is worth saying and not worth reddening a repo for.

`schedule_check` is **advisory**. A stale sprint plan or an overdue decision is a fact about the
*project*, not a defect in the change — blocking a commit on it teaches people to bypass the gate,
which is worse than the condition. That needed a new concept in the driver: `advisory: true`. The
step **runs and prints**, its failure is named in the closing banner, and **GREEN is never printed
bare** while one is failing. It is explicitly not the silent skip this driver exists to prevent.
Right now it fails honestly: the plan has no sprint covering today and D11 is overdue.

**2. `Reviewer lens` is consulted in the two lanes that required it and never read it.** `/ba` B3
pastes the lens of every loaded competency into the challenger's prompt, the rule `/qa` V6 already
runs. `/pm` has no challenger for the ordering, so P1 reads the lens back as a **self-check** —
nobody else will ask those questions, and a lens item the picker cannot answer is a pick that
cannot be defended.

**3. D14 — a deliberately forked file no longer parks a `.new` forever.** `.vteam/manifest.json`
takes an `owned: [paths]` list. A declared path is never clobbered **and never parked**; instead
`vteam update` reports once that upstream moved under a file this repo owns. The chore was real —
it bit three times in one day on the field repo, and the third time the fork silently failed to
receive a new gate step, which is a feature freeze, not a tidying task.

**4. D15 — the `P` prefix collision stays.** `role:` already disambiguates, and VT-20 closed the
trap: `competency_check` resolves `loads` against that role's workflow and reds a value naming no
step there. Renaming a step vocabulary would touch every workflow, doc and frontmatter citing it,
to fix an ambiguity that is no longer reachable.

## Acceptance criteria (testable)

1. `gate.sh` runs an `evd-ui` step; a closed ticket whose dev pack breaks the standard reds it, and
   a pack that predates the layout is reported with its image count and does **not** red.
2. `gate.sh` runs a `schedule` step that **fails today** and the gate still exits 0 — with
   `— 1 ADVISORY FAILED: schedule` on the GREEN line and the checker's own output printed above it.
3. `gate.py --selftest` covers `advisory` in four directions: fails-without-blocking, still-prints,
   banner-on-GREEN, passes-silently, and never softens a hard red.
4. `grep -ci 'reviewer lens'` returns > 0 for `ba.md` and `pm.md`.
5. A path listed in the manifest's `owned` survives `vteam update` with **no `.new` written** and a
   `📌 … OWNS` line printed. Demonstrated on the field repo's forked `gates.yaml`.
6. `.githooks/pre-push` is **not** declared owned — D11 is still open and silencing its `.new`
   would hide a pending decision behind a convenience.

## Out of scope

- D11 itself. Adopting the packaged hook changes how the owner pushes; analysed in D11's row,
  waiting on them.
- Filling `/pm`'s missing P3. A gap with a reason beats a step invented to tidy a sequence.
