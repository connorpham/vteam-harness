# VT-40: two lanes can hash to one port — 800 buckets, and CI drew the collision the next day
- status: In Review
- labels: parallel, flaky, bug
- estimate: 0.25d
- type: Bug

**30-second summary:** VT-35 derives a lane's port as `3100 + fnv1a(path[#lane]) % 800`. With 800
buckets a collision is a coin flip once a worktree runs a few lanes, and the collision IS the
failure that helper exists to prevent — two agents on one port. CI drew it the day after the helper
shipped: `lane_env selftest: FAIL — reviewer lane R1 derived the author's port 3724`, on Linux only,
because the e2e fixture path is a fresh temp directory every run. The derived port is now a
starting point: the helper steps forward until no other lane's marker claims the port, says so in
its output, and records where the lane actually landed.

## Why
A flaky selftest is bad; a real port collision between an author and a reviewer agent is worse —
it is E13 from the benchmark, the finding VT-35 exists to close. Found by CI on PR #89, which was
red for a reason that had nothing to do with that ticket. Spec: `core/scripts/lane_env.sh`,
benchmark finding E13 (`docs/BENCHMARK.md`). no UI.

## Acceptance criteria
- Given a port another lane's marker already claims / When a lane derives its environment / Then it steps forward within 3100–3899 to the first unclaimed port and prints that it did.
- Given the same worktree and lane twice / When derived twice / Then the environment is byte-identical (a lane must not step over its own marker).
- Given the selftest / When run repeatedly / Then it passes every time, including a deliberately planted collision.

## Out of scope
`init.derivePort` (the app port written at init time) shares the same 800-bucket space and has no marker to consult; a collision there shows up as a normal port-in-use error, and unifying the two allocators is a larger change than this bug needs.
