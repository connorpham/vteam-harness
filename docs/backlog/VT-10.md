# VT-10: parallel-worktree mode — gates that read siblings from git, bookkeeping never scope, merged branches not in flight, commit attribution by leading key

- status: In Review
- assignee: Connor Pham
- estimate: 0.75d
- labels: gates, parallel, no UI

## Why

First live `/team` run with `team.parallel: 2` on a real Orca transport (two
claude/opus workers in child worktrees, testbed project, 2026-09-09). Both
workers hit the same class of defect within minutes and reported it over the run
mailbox with proofs: the parallel-mode gates read a SIBLING ticket's tasksheet
from the local filesystem, which in a split worktree is never there. The PM
patched the installed runtime copies under `.vteam/scripts/` (testbed commits
5cdd4bb, 9630327, 68be1e8, b772bc9-corrected-by-6ceef7f) so the run could
finish honestly; this ticket ports those fixes into core with their selftests.

Defects, each proven live:
1. `parallel_check.discover()` read `evd/<T>/dev/tasksheet.md` from disk →
   structurally RED for every worker in worktree mode ("no CODE-SCOPE" for the
   sibling). Worktrees share one object store, so the committed tasksheet is
   readable as `git show <branch>:<path>`.
2. `coord_check.scope_of()` — same read → a correct handoff went RED because
   the receiver's CODE-SCOPE looked empty.
3. Both agents, told to append the handoff row to `docs/pm/coordination.md`,
   listed that path in CODE-SCOPE → parallel_check "share edit territory" on the
   coordination log itself. Bookkeeping homes (`paths.pm`, `paths.evidence`,
   `paths.qa`) are shared by design and must never count as edit territory.
4. `parallel_check` counted branches already MERGED into the protected branch as
   in-flight (they linger locally; a worktree may keep one checked out) → the
   third ticket would have exceeded the cap of 2.
5. `graph_check` attributed a PM chore commit whose subject merely MENTIONED
   "TB-5" in prose to TB-5's CODE-SCOPE → false derailment red. A commit belongs
   to a ticket only when the key LEADS the subject (`TB-5 …`, `feat(TB-5): …`,
   `[TB-5] …`).

## Acceptance criteria (testable)

1. **Given** a repo where ticket B's tasksheet exists only as a commit on branch
   `feat/B-…` (not on disk), **When** `parallel_check.py` runs from another
   checkout of the same repo, **Then** B's CODE-SCOPE is read from git and the
   gate is GREEN for disjoint scopes; **and Given** no committed tasksheet,
   **Then** the red names it as "tasksheet missing on <branch>, not committed",
   not as a phantom empty scope. Selftest proves it with an off-disk git fixture.
2. **Given** the same layout, **When** `coord_check.py` verifies a handoff whose
   receiver's tasksheet is only in git, **Then** the handoff is "reflected" (GREEN);
   selftest fixture as above; `VT-1` must not match a `VT-11` branch.
3. **Given** two in-flight scopes that both list `docs/pm/coordination.md` (or
   any path under `paths.pm` / `paths.evidence` / `paths.qa`), **When**
   `parallel_check.py` runs, **Then** those paths are printed as "bookkeeping
   paths not counted as edit territory" and cause no conflict; **and** a real
   overlap under code paths is still RED (selftest boundary pair).
4. **Given** local branches `feat/A-…` already merged into the protected branch
   (including one checked out in a worktree, i.e. decorated `+` by `git branch`),
   **When** `parallel_check.py` runs, **Then** they are not counted toward
   `team.parallel`; the count line reports only unmerged branches.
5. **Given** a commit whose subject is `chore: … found by the TB-5 worker`,
   **When** `graph_check.py` checks TB-5's scope, **Then** the commit is NOT
   attributed to TB-5; **and Given** subjects `TB-5 …`, `feat(TB-5): …`,
   `merge(TB-5): …`, `[TB-5] …`, **Then** they ARE attributed (selftest covers
   both directions; the existing 7 mutations stay red).
6. Doctrine: `core/doctrine/parallel-transport.md` + `core/workflows/dev.md` T1
   state that in parallel mode the tasksheet is COMMITTED as the first commit
   (siblings' gates read it via git), that bookkeeping paths are never
   CODE-SCOPE, and that `orca worker-start` into a NEW worktree needs the folder
   pre-trusted (Claude's trust dialog eats the injected prompt →
   `agent_prompt_stalled`) — `orca_team.sh` gains a `trust <path>` helper or the
   doctrine names the exact `~/.claude.json` field.
7. `gate.sh` GREEN, `doctor` 32 selftests green, `tests/e2e.mjs` green with the
   README counts unchanged (no new selftest-bearing scripts), no unresolved
   `{vars}`; evidence under `evd/VT-10/dev/` with the three selftests' output and
   a live probe on a two-worktree fixture.

[R1] What was done

The framework can put several AI developers to work at the same time, each in their own private copy of the project folder. The first time that was actually tried for real — two developers, 9 September — both of them hit the same class of problem within minutes: the safety checks that are supposed to police parallel work kept refusing perfectly honest work. Five separate defects, all with the same root cause: those checks were written assuming everyone shares ONE folder. This ticket fixes all five, and writes down the three operating rules the run had to learn the hard way so the next one does not repeat it.

[R2] Impact scope

Four framework files under core/ (three safety checks and one helper script), plus three pieces of written guidance, plus the machine-generated copies of all of them. Searched every function I touched: each has exactly one caller, all inside its own file, so nothing else in the framework can be surprised. No database, no schema, no migration, no user interface — this repo is a command-line framework. The one thing that reaches outside the project folder is the new `trust` command, which edits the user's own Claude Code settings file; that is why it backs the file up before writing, keeps the file's original permissions, and refuses a settings file it cannot read rather than replacing it.

[R3] Technical

parallel_check now reads a sibling ticket's declared file scope out of git rather than off the local disk (worktrees share one object store, so `git show <branch>:<path>` sees what the filesystem cannot); discounts the bookkeeping homes paths.pm / paths.evidence / paths.qa, which are shared by design; and decides "already landed" by content and topology (merge, squash and rebase all leave different traces) rather than by whether the protected branch merely moved. coord_check reads the receiving ticket's scope the same way, newest branch first. graph_check attributes a commit to a ticket only when the key LEADS the subject line. orca_team.sh gains `trust <path>`, which sets projects["<abs path>"].hasTrustDialogAccepted in ~/.claude.json.

[R4] Tested

Gate GREEN (9 steps, 1 declared skip). Doctor: 32 selftests green, 115 framework files intact. End-to-end suite: 164/164. All three patched checks pass their own selftest in both the source and installed copies. Fourteen mutation proofs — each new rule reverted one at a time to prove the tests can actually fail — all fourteen go red. Plus a live probe on a real three-worktree repository, which is the only place these checks' true behaviour can be observed (they are switched off in this repo, where parallel mode is set to 1).

[R6] Notes for QA

The interesting verification is not in this repo — parallel mode is off here, so both changed checks are deliberately inert-green. To see them work, reproduce the probe: the script is transcribed at the end of cmd_probe.md and builds a throwaway three-worktree repository. Worth re-running independently: the boundary pairs, since each fix must NOT disarm the check it touches. An uncommitted tasksheet must still go red (naming the remedy); a genuine overlap on product code must still go red; a commit whose subject leads with the ticket key must still be caught straying outside its declared scope, on the very same files that a merely-mentioning commit is correctly ignored for. For the trust command, please use a sandboxed HOME — never the real settings file.

[R7] Open issues

Three side findings, none fixed here because all are outside this ticket's declared scope, and each deserves its own ticket. First and most important: this repository's own pre-push hook is a stale 36-line version that does not run review_check.py, so the committed-review fence the dev lane promises is not actually armed here — the framework's current hook does have it, and `update` parks it beside the old one rather than overwriting. Second: the gate has no shell-syntax check, and during this ticket a stray apostrophe inside a shell script's embedded Python silently broke the new trust command while every gate stayed green; only running the command caught it. Third: the code map ranked two of the three files this ticket changes out of a query that named their exact subject matter. One accepted non-blocking review question also remains: a first-parent walk inside the landed-branch check is recomputed per branch and kept as a list; measured at 69 commits here, with the mechanical fix recorded.
