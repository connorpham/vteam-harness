# VT-10: parallel-worktree mode — gates that read siblings from git, bookkeeping never scope, merged branches not in flight, commit attribution by leading key

- status: In Progress
- assignee: Connor Pham
- estimate: 0.75d
- labels: gates, parallel, no UI

## Why

First live `/team` run with `team.parallel: 2` on a real Orca transport (two
claude/opus workers in child worktrees, testbed project, 2026-09-09). Both
workers hit the same class of defect within minutes and reported it over the run
mailbox with proofs: the parallel-mode gates read a SIBLING ticket's tasksheet
from the local filesystem, which in a split worktree is never there. The PM
patched the installed runtime copies under `.vteam/scripts/` (testbed commits
5cdd4bb, 9630327, 68be1e8, b772bc9-corrected-by-6ceef7f) so the run could
finish honestly; this ticket ports those fixes into core with their selftests.

Defects, each proven live:
1. `parallel_check.discover()` read `evd/<T>/dev/tasksheet.md` from disk →
   structurally RED for every worker in worktree mode ("no CODE-SCOPE" for the
   sibling). Worktrees share one object store, so the committed tasksheet is
   readable as `git show <branch>:<path>`.
2. `coord_check.scope_of()` — same read → a correct handoff went RED because
   the receiver's CODE-SCOPE looked empty.
3. Both agents, told to append the handoff row to `docs/pm/coordination.md`,
   listed that path in CODE-SCOPE → parallel_check "share edit territory" on the
   coordination log itself. Bookkeeping homes (`paths.pm`, `paths.evidence`,
   `paths.qa`) are shared by design and must never count as edit territory.
4. `parallel_check` counted branches already MERGED into the protected branch as
   in-flight (they linger locally; a worktree may keep one checked out) → the
   third ticket would have exceeded the cap of 2.
5. `graph_check` attributed a PM chore commit whose subject merely MENTIONED
   "TB-5" in prose to TB-5's CODE-SCOPE → false derailment red. A commit belongs
   to a ticket only when the key LEADS the subject (`TB-5 …`, `feat(TB-5): …`,
   `[TB-5] …`).

## Acceptance criteria (testable)

1. **Given** a repo where ticket B's tasksheet exists only as a commit on branch
   `feat/B-…` (not on disk), **When** `parallel_check.py` runs from another
   checkout of the same repo, **Then** B's CODE-SCOPE is read from git and the
   gate is GREEN for disjoint scopes; **and Given** no committed tasksheet,
   **Then** the red names it as "tasksheet missing on <branch>, not committed",
   not as a phantom empty scope. Selftest proves it with an off-disk git fixture.
2. **Given** the same layout, **When** `coord_check.py` verifies a handoff whose
   receiver's tasksheet is only in git, **Then** the handoff is "reflected" (GREEN);
   selftest fixture as above; `VT-1` must not match a `VT-11` branch.
3. **Given** two in-flight scopes that both list `docs/pm/coordination.md` (or
   any path under `paths.pm` / `paths.evidence` / `paths.qa`), **When**
   `parallel_check.py` runs, **Then** those paths are printed as "bookkeeping
   paths not counted as edit territory" and cause no conflict; **and** a real
   overlap under code paths is still RED (selftest boundary pair).
4. **Given** local branches `feat/A-…` already merged into the protected branch
   (including one checked out in a worktree, i.e. decorated `+` by `git branch`),
   **When** `parallel_check.py` runs, **Then** they are not counted toward
   `team.parallel`; the count line reports only unmerged branches.
5. **Given** a commit whose subject is `chore: … found by the TB-5 worker`,
   **When** `graph_check.py` checks TB-5's scope, **Then** the commit is NOT
   attributed to TB-5; **and Given** subjects `TB-5 …`, `feat(TB-5): …`,
   `merge(TB-5): …`, `[TB-5] …`, **Then** they ARE attributed (selftest covers
   both directions; the existing 7 mutations stay red).
6. Doctrine: `core/doctrine/parallel-transport.md` + `core/workflows/dev.md` T1
   state that in parallel mode the tasksheet is COMMITTED as the first commit
   (siblings' gates read it via git), that bookkeeping paths are never
   CODE-SCOPE, and that `orca worker-start` into a NEW worktree needs the folder
   pre-trusted (Claude's trust dialog eats the injected prompt →
   `agent_prompt_stalled`) — `orca_team.sh` gains a `trust <path>` helper or the
   doctrine names the exact `~/.claude.json` field.
7. `gate.sh` GREEN, `doctor` 32 selftests green, `tests/e2e.mjs` green with the
   README counts unchanged (no new selftest-bearing scripts), no unresolved
   `{vars}`; evidence under `evd/VT-10/dev/` with the three selftests' output and
   a live probe on a two-worktree fixture.
