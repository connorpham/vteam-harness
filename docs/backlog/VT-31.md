# VT-31: `vteam init` leaves `app:` empty in a Next.js repo and pins no port — the lanes had nothing to drive, and two arms shared :3000
- status: In Review
- labels: init, environment, benchmark
- estimate: 0.25d
- type: Bug

**30-second summary:** benchmark finding E2 (2026-09-03): the vteam arm's first hour went to
discovering that `app.start/url/health` were empty, so `app_check.sh` printed `APP: SKIP` and no
browser step could run. E7/E15: both arms on one machine defaulted to port 3000; `app_check`
reported the OTHER arm's server as UP, and a whole a11y suite measured a stranger's app. `init`
now prefills the block for any repo whose `package.json` declares `next`, on a port derived from
the checkout's real path, and says so in its summary.

## Why
A gate that measures someone else's app produces evidence that is wrong in the most convincing
way. Spec: `~/Documents/vteam-vs-bmad/arm-a-vteam/RUNLOG.md` rows E2, E7, E15 (owner's machine);
docs/GUIDE.md `app:` bullet. no UI.

## Acceptance criteria
- Given a repo whose package.json declares `next` / When `vteam init --yes` runs / Then `vteam.config.yaml` carries `start: "npx next dev -p <port>"`, `url: "http://127.0.0.1:<port>"`, `health: "/"`, and init prints the pinned port and why.
- Given two checkouts at different paths / When each is initialised / Then their ports differ; given one checkout reached by two spellings (symlink) / Then the port is the same.
- Given a repo without `next` / When initialised / Then the `app:` block is empty exactly as before.
- Given tests/e2e.mjs / When the detection is disabled (code-only mutation) / Then the new checks are RED; with the fix, GREEN, and README's check count matches the suite.

## Out of scope
Choosing a port for non-Next apps (no runnable command can be derived); verifying at gate time that the listener on the port belongs to this checkout (VT-30 app_check ownership check); editing the repo's own package.json scripts.
