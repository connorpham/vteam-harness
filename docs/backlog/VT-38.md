# VT-38: the plan counted 21 tickets in flight when one was running — a merged branch is not work
- status: In Review
- labels: graph, board-hygiene, bug
- estimate: 0.5d
- type: Bug

**30-second summary:** VT-37's planner read `git branch` and called every local `feat|fix/<KEY>-*`
branch work in flight. Nobody deletes branches after a merge, so 32 of this repo's 33 branches were
history and the plan reported **21 in flight against a true number of 1** — the whole team's
capacity hidden behind leftovers. In flight now means an UNMERGED branch, local or pushed. The
other half of the same lie: nine tickets said In Progress with nothing running, because the status
was never moved after the work shipped. The plan reports that as stale WIP and `graph_check` warns
about it; the nine were then corrected against the evidence.

## Why
A planner that miscounts capacity is worse than no planner: it says "everything is busy" and the
lane believes it. Found the day after VT-37 shipped, by reading its own output against `git branch
--no-merged`. Spec: `src/cli/graph.mjs` (buildPlan/inFlightKeys), `core/scripts/graph_check.py`. no UI.

## Acceptance criteria
- Given a branch already merged into `git.protected_branch` / When the plan runs / Then its ticket is NOT in flight; given an unmerged branch (local or `remotes/*`) / Then it IS, and it leaves the waves.
- Given a ticket In Progress with no unmerged branch and nothing blocking it / When the plan runs / Then it appears under STALE WORK IN PROGRESS with the reason and stays schedulable; when something blocks it, it is listed as blocked instead.
- Given the same condition / When `graph_check` runs / Then it is a WARNING naming the tickets, never a failure — it is a fact about the board, not about the change under review.
- Given no protected branch locally (a fresh clone, a CI checkout) / When either reads branches / Then it falls back to listing all of them rather than concluding that nothing is running.

## Out of scope
Deleting the 32 merged local branches (housekeeping for the owner); changing the ledger grammar so an unmeasured row can be honest — that is the decision queue's newest row, filed by this ticket and deliberately not implemented here.
