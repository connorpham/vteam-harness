# 24/7 operations — scheduled sessions on a subscription plan

> Goal: the team keeps working overnight and over weekends with nobody watching, on
> a **subscription** plan (Claude Pro/Max and equivalents) rather than metered API
> billing. What that buys is **unattended continuity** — not unlimited throughput.
> Sessions start on a clock, work until the work or the usage window runs out, and
> leave the board in a state the next session can pick up cold.
>
> This is the per-OS appendix. The rules live in `ops.md`; the plists, units and
> cron lines live here. Where the two disagree, `ops.md` wins.

## 1. 24/7 is many short sessions, not one immortal session

A session is a **shift**, not a daemon. Every scheduled run does exactly this:

open the repo → read the board, the ledger and the decision queue → `/team` → desk
report + session minute → exit.

Nothing survives in memory between shifts, and nothing needs to. A long session is
not more productive than four short ones — it is only harder to resume.

Everything a cold session needs already exists, and each mechanism has one home:

| What a resuming session must know | The mechanism that answers it | Home |
|---|---|---|
| what was already done, blocked or failed | the dispatch ledger `{paths.pm}/log.md` — append-at-end, single writer, `log_check`ed | `ops.md` §1, §7 |
| whether someone is holding this ticket right now | the In Progress **claim** (`claimed <timestamp> · <branch>`) and its TTL | `raci.md` §2 |
| what may not be decided without the owner | the decision queue `{paths.pm}/decisions.md` + `autonomy.exemptions` | `ops.md` §3 |
| what the team said and concluded last shift | the session minute `{paths.pm}/sessions/YYYY-MM-DD-hhmm.md` | `team.md` T2 |
| which work is real work | the sprint plan + backlog draft + the queue's ADR section — a scheduled session invents no work for itself | `team.md` loop guard 4 |

**Consequence:** a killed shift is not an incident. A crash, a closed lid, a spent
usage window — the next timer opens the same books and continues. There is no
resume *state* to store — a stored checkpoint would be a second source of truth
nothing keeps honest (it could say "review done" while `dev/review.md` does not
exist). What does exist is a **reader**: `npx vteam-harness resume <KEY>` opens
those same books (claim, branch, tasksheet, review dossier, QA verdict, ledger
rows) and prints the furthest *proven* stage plus the next dispatch — one command
instead of five lookups, derived on every run, so it cannot go stale or lie.

## 2. Subscription reality, stated plainly

Subscription plans do not sell hours; they meter usage in **rolling windows**
(Claude's are 5-hour windows, with the allowance inside a window depending on plan
and subject to change — **check your plan's current limits, and re-check them; this
file will not quote a number it cannot guarantee**). Weekly ceilings exist on some
plans too. Everything below is written so the numbers can move without the doctrine
moving.

The principle, which does not move:

1. **Schedule per window, not per hour.** One session per usage window is the unit.
   Four to five well-spaced shifts a day is the shape that fits a 5-hour cadence;
   more starts is not more work, it is more collisions. The recipes below fire at
   07/12/17/22 — four ticks five hours apart, one long overnight gap; add an 03:00
   tick if you want that fifth window worked too.
2. **Let a session end when the window is spent.** A session that runs out of
   allowance mid-ticket should stop, not thrash. The desk report is thinner; that is
   the honest outcome.
3. **A spent window is a break, not a failure** (`ops.md` §1). The board shows where
   work stopped; the next timer fires anyway.
4. **The exemptions stay absolute.** Real money, legal, purchasing, credentials and
   secrets, deletion of real data — never auto-decided, at any autonomy level, at
   any hour, however much allowance is left (`ops.md` §3).

**Never promised here:** unlimited 24/7 throughput, a fixed number of tickets per
night, or that a subscription behaves like an API budget. Promised: the machine
tries on a schedule, and nothing is lost when it can't finish.

**Two things are genuinely undocumented — plan for them, don't guess at them.**
① What a non-interactive run does the instant its window is spent is not specified
anywhere: it may fail, it may return early. Treat a non-zero exit *or* an
implausibly thin desk report as "window spent", and let the next timer handle it.
② How long a subscription login survives unattended. Subscription credentials come
from an *interactive* login held in the OS keychain — there is no subscription
API-key environment variable, and a runtime mode that deliberately skips the keychain
will not see them at all. Expect an occasional interactive re-login; you notice it as
a run of failed shifts and a gap on the board, which is exactly why §7 insists those
failures stay loud.

**Cut off mid-ticket?** That case is already designed for: the ticket sits In
Progress with a claim, the claim's TTL expires, and the PM recovery lane treats a
claim past TTL with no remote branch or worklog as orphaned and reclaims it
(`raci.md` §2 — the one home of the TTL number). No overnight babysitting, no
special handling. What you must NOT do is add a second concurrent session to "use
the window better": that manufactures the exact claim collisions the TTL machinery
exists to clean up. Prevent, don't repair — see §4.

## 3. The scheduled invocation

Tool-agnostic core: **one command, non-interactive, in the repo, with a lock, and a
log of what it printed.** Any agent CLI that can start a workday without a TTY fits.
Claude Code is the worked example:

```bash
# -p / --print: one turn, print, exit. No TTY, no interactive session.
claude -p "Run the vteam workday: use the 'team' skill in this repo, full workday."
```

**Why prose and not `/team`.** vteam renders its workflows as native skills for
Claude Code (`.claude/skills/team/SKILL.md`), and *typed slash commands are not
reliably available in print mode* — the documented set of commands accepted by `-p`
is small and version-dependent. Naming the skill in the prompt is the version-proof
form. If `claude -p "/team"` works on your version, use it — but verify it by hand
once before a timer depends on it: a scheduled shift that silently did nothing
because the prompt was not understood is the worst failure mode in this file.

Rules for the unattended form, in order of importance:

- **The autonomy posture is config, not a flag.** `autonomy.level` in
  `vteam.config.yaml` decides what waits for the owner; the doctrine default stays
  `assisted` plus the exemption list. Be clear-eyed about what that means overnight:
  at `assisted`, work reaches In Review and green PRs **wait** — the night produces
  reviewed, evidenced, mergeable work, not merges. Wanting merges to happen while
  you sleep is a deliberate move to `full` + `autonomy.self_merge: true`, taken with
  eyes open, and even then the exemptions and every quality gate hold.
- **The fence and the gates run regardless of the hour.** `/verify`, the review
  standard, the evidence gate, the challengers, the pre-push hook — a 03:00 session
  is checked exactly like a 15:00 one. There is no night mode.
- **Permission prompts must be impossible, not answered.** An unattended run that
  stops on a confirmation dialog hangs until the timeout — worse than failing. Decide
  the permission posture *before* scheduling: pre-allow the tools the lanes need in
  your tool's settings, or use its permission flags. Claude Code has a
  `--permission-mode` flag and a `--dangerously-skip-permissions` escape hatch; the
  accepted values move between versions, so **`claude --help` is the authority for
  yours** — do not copy a flag value out of a document, including this one. Whatever
  you pick, it changes *who gets asked*, never *which gates run*.
- **Read the exit code, log the output, trust neither alone.** A print-mode run exits
  0 on success and non-zero on failure, but the failure *reason* is not encoded in the
  code — so keep the printed output (the runner below does), and reach for a machine-
  readable `--output-format` (`text` / `json` / `stream-json`) only if something
  downstream actually parses it.
- **Cap the shift.** Use the scheduler's own timeout (`TimeoutStartSec=` under
  systemd; `timeout 4h …` where GNU coreutils is present) so a wedged run dies before
  the next tick. `/team`'s loop guards are the in-session ceiling — one attempt per
  item, the `n=N` cap, the hard ceiling of 12 items, stop on a zero-progress sweep
  (`team.md`).
- **Never resolve git history unattended.** Sync fast-forward-only; a non-fast-forward
  is an owner problem, and the run should stop and say so rather than merge at 03:00.

### The runner script — shared by all three recipes

`~/bin/vteam-workday.sh` (`chmod +x`). It is deliberately dull: lock, sync, run, log.

```bash
#!/usr/bin/env bash
# One vteam shift. Tool-agnostic: change the AGENT line for another CLI.
set -uo pipefail

REPO="${VTEAM_REPO:-$HOME/src/myproject}"
RUNS="${VTEAM_RUNS:-$HOME/.local/state/vteam}"
cd "$REPO" || exit 1

# Lock inside the git dir: never committed, never manifest-tracked, dies with the
# clone. `git rev-parse` because .git is a FILE, not a directory, in a worktree.
LOCK="$(git rev-parse --git-dir)/vteam-workday.lock"
mkdir -p "$RUNS"
STAMP="$(date +%Y-%m-%d-%H%M)"
RUN_LOG="$RUNS/$STAMP.log"

# --- one shift per machine, per repo (portable: macOS has no flock) -------------
if ! mkdir "$LOCK" 2>/dev/null; then
  pid="$(cat "$LOCK/pid" 2>/dev/null || true)"
  if [ -n "$pid" ] && kill -0 "$pid" 2>/dev/null; then
    echo "skipped: shift $pid still running" >>"$RUN_LOG"; exit 0
  fi
  echo "stale lock from pid ${pid:-unknown} — taking over" >>"$RUN_LOG"
  rm -rf "$LOCK"; mkdir "$LOCK" || exit 1
fi
echo $$ >"$LOCK/pid"
trap 'rm -rf "$LOCK"' EXIT INT TERM

# --- sync, but never reconcile history unattended ------------------------------
if git remote get-url origin >/dev/null 2>&1; then
  if ! git pull --ff-only >>"$RUN_LOG" 2>&1; then
    echo "not a fast-forward — owner must reconcile; no work this shift" >>"$RUN_LOG"
    exit 75                                 # EX_TEMPFAIL: the next timer retries
  fi
fi

# --- the shift ------------------------------------------------------------------
echo "=== shift $STAMP starting ===" >>"$RUN_LOG"
claude -p "Run the vteam workday: use the 'team' skill in this repo, full workday." \
  >>"$RUN_LOG" 2>&1                          # AGENT line — swap for another CLI
rc=$?
echo "=== shift $STAMP exit=$rc ===" >>"$RUN_LOG"
exit "$rc"                                   # loud on failure: the scheduler logs it
```

One run, one file, in one directory. A missing file *is* the gap: a night with three
files instead of four says a shift never started, and that is exactly the signal you
want. The durable record stays in git — the ledger row and the session minute; this
log is the printed desk report and the exit code, kept where a scheduler can be
debugged.

## 4. Per-OS recipes

### macOS — launchd + `caffeinate`

`~/Library/LaunchAgents/com.vteam.workday.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>com.vteam.workday</string>
  <key>ProgramArguments</key>
  <array>
    <string>/usr/bin/caffeinate</string>
    <string>-i</string>
    <string>/bin/bash</string>
    <string>-lc</string>
    <string>$HOME/bin/vteam-workday.sh</string>
  </array>
  <key>EnvironmentVariables</key>
  <dict>
    <key>PATH</key>
    <string>/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin</string>
    <key>VTEAM_REPO</key>
    <string>/Users/you/src/myproject</string>
    <key>VTEAM_ACTOR</key>
    <string>scheduler</string>
  </dict>
  <key>StartCalendarInterval</key>
  <array>
    <dict><key>Hour</key><integer>7</integer><key>Minute</key><integer>0</integer></dict>
    <dict><key>Hour</key><integer>12</integer><key>Minute</key><integer>0</integer></dict>
    <dict><key>Hour</key><integer>17</integer><key>Minute</key><integer>0</integer></dict>
    <dict><key>Hour</key><integer>22</integer><key>Minute</key><integer>0</integer></dict>
  </array>
  <key>RunAtLoad</key>
  <false/>
  <key>StandardOutPath</key>
  <string>/Users/you/Library/Logs/vteam-workday.out.log</string>
  <key>StandardErrorPath</key>
  <string>/Users/you/Library/Logs/vteam-workday.err.log</string>
</dict>
</plist>
```

```bash
plutil -lint ~/Library/LaunchAgents/com.vteam.workday.plist     # syntax first
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.vteam.workday.plist
launchctl print gui/$(id -u)/com.vteam.workday | head -40       # state, last exit
launchctl kickstart -k gui/$(id -u)/com.vteam.workday           # run one shift now
launchctl bootout gui/$(id -u)/com.vteam.workday                # remove
```

Notes that matter:

- **launchd has no "every 5 hours".** `StartCalendarInterval` takes a list of ticks —
  write them out, as above. `StartInterval` (seconds) is the alternative when you
  care about spacing rather than clock times; the two are mutually exclusive per job.
- **launchd will not run a second copy of the same Label** while one is running, so
  the plist covers scheduled-vs-scheduled overlap. It does **not** cover your own
  manual `/team` in a terminal — that is what the runner's lock is for.
- **Keep-awake:** `caffeinate -i` in the run wrapper blocks idle sleep for exactly
  the length of the shift, which is cheaper than keeping the machine up all night.
  For the always-on variant, `ops.md` §2 and `provenance.md` describe the reference
  setup (a `caffeinate -is` LaunchAgent with `RunAtLoad` + `KeepAlive`).
- **Physical reality no software fixes:** a closed lid sleeps the Mac regardless
  (absent external display + power), and a sleeping machine runs missed calendar
  jobs *late*, on wake — late, not lost.

**"The AI stopped running overnight" — diagnose in this order.** Three states get
confused; only one of them stops work:

| State | Scheduled jobs |
|---|---|
| Screen locked, or display asleep | keep running |
| Machine asleep | suspended — jobs are missed, then run late on wake |
| User logged out | LaunchAgents are gone until next login |

So locking the screen is fine. Sleep is the culprit, and the default that causes it
is easy to miss:

```bash
pmset -g custom | sed -n '/AC Power/,/^$/p'   # is `sleep` nonzero on AC?
pmset -g sched                                 # empty = nothing ever wakes this Mac
```

A machine meant to work shifts should not idle-sleep while plugged in:

```bash
sudo pmset -c sleep 0        # on AC: never idle-sleep (display may still sleep)
sudo pmset -c disksleep 0    # don't park the disk mid-shift either
```

`-c` scopes both to AC power, so battery behaviour is untouched. If the machine
*must* sleep, schedule a wake a few minutes before a shift —

```bash
sudo pmset repeat wakeorpoweron MTWRFSU 06:55:00
```

— but know the limit: macOS keeps exactly **one** `repeat` schedule, so this covers
one shift a day, not four. For genuine round-the-clock work, the honest answer is a
machine that does not sleep (a desktop left on, a mini PC, a VM), not a laptop
fighting its power manager.

### Linux — systemd user timer + `systemd-inhibit`

`~/.config/systemd/user/vteam-workday.service`:

```ini
[Unit]
Description=vteam scheduled workday session
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
WorkingDirectory=%h/src/myproject
Environment=VTEAM_REPO=%h/src/myproject
Environment=VTEAM_ACTOR=scheduler
ExecStart=/usr/bin/systemd-inhibit --what=idle:sleep --who=vteam \
          --why="scheduled workday session" %h/bin/vteam-workday.sh
TimeoutStartSec=4h
```

`~/.config/systemd/user/vteam-workday.timer`:

```ini
[Unit]
Description=Run a vteam workday session four times a day

[Timer]
OnCalendar=*-*-* 07,12,17,22:00:00
Persistent=true
AccuracySec=1min
RandomizedDelaySec=2min
Unit=vteam-workday.service

[Install]
WantedBy=timers.target
```

```bash
systemctl --user daemon-reload
systemctl --user enable --now vteam-workday.timer     # the TIMER is enabled…
systemctl --user list-timers vteam-workday.timer      # …next/last fire
systemctl --user start vteam-workday.service          # run one shift now
journalctl --user -u vteam-workday.service -n 50      # what it printed
loginctl enable-linger "$USER"                        # timers run with nobody logged in
```

Notes that matter:

- **The service carries no `[Install]` section on purpose** — you enable the timer,
  never the service. An enabled oneshot service would fire at boot as well.
- **`Persistent=true`** runs a tick that was missed while the machine was off or
  asleep, once, on the next start. Same law as macOS: late, not lost.
- **`loginctl enable-linger`** is the difference between "works while I'm logged in"
  and 24/7 on a server or headless box.
- **`systemd-inhibit --what=idle:sleep`** blocks sleep for the duration of the shift
  only. Add `handle-lid-switch` to the `--what` list if a laptop must survive a
  closed lid — and expect firmware to have opinions.

### Anywhere — cron + `flock`

```cron
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
VTEAM_REPO=/home/you/src/myproject

0 7,12,17,22 * * * /usr/bin/flock -n /tmp/vteam-workday.lock /home/you/bin/vteam-workday.sh
```

- `flock -n` is the whole point: **two shifts must never overlap on one machine.**
  Without it a slow shift and the next tick both open the same repo, both claim
  tickets, and you spend the morning reading the TTL machinery's cleanup instead of a
  desk report. Prevent, don't repair.
- `flock` ships with util-linux — **it is not on stock macOS**; there the runner's own
  `mkdir` lock (§3) is the guard.
- cron's environment is nearly empty: set `SHELL` and `PATH` in the crontab, use
  absolute paths, and remember cron treats `%` as a field separator — escape it as
  `\%` if a command line ever needs one.
- cron does **not** run missed jobs after a sleep or shutdown. A laptop that sleeps
  through 22:00 simply skips that shift. `anacron`-style tools or the systemd/launchd
  recipes above are the fix.

### One repo, one shift — the standing rule

Two sessions on one repository is not parallelism, it is claim collision. The lock
covers one machine. If you want a second machine working the same repo, treat it as
`team.size > 1`: read `DESIGN.md` §7 first, give it its own `VTEAM_ACTOR`, and expect
the WIP limit and TTL to be prose the agents follow, not gates.

## 5. What does not relax at 03:00

Nothing. Written out, because "nobody is watching" is the oldest excuse there is
(`red-flags.md`):

| At 03:00, unattended | Still true |
|---|---|
| Quality gates | `/verify` in full, cheapest-first; a skipped step declares itself or the run fails |
| Reviews | fresh reviewer agents to the written standard; no self-approval; APPROVE without a "what I tried to break" list is invalid |
| Evidence | files that exist and open, before the verdict — a nightly claim with no artifact is not a claim |
| The push fence | no direct push to the protected branch, no code without its review dossier, secret scan with no hatch; every named hatch use lands in `{paths.pm}/hatch-log.md` |
| The exemptions | real money, legal, purchasing, credentials, deletion of real data — untouched, queued, reported |
| Questions | a question **waits for the owner**. `autonomy: full` buys a *provisional decision with a paper trail* (🟡, stated reversal cost, `pending-acceptance`), never an invented answer |
| Loop guards | one attempt per item, the item cap, stop on a zero-progress sweep, twice-failed work escalated to the queue instead of retried |

**Logging is part of the rail, not a nicety.** Each shift appends its desk report to
its run log (§3) and writes its session minute to `{paths.pm}/sessions/`, plus one
ledger row per item — including abandoned items, with reasons. Evidence that only
lives in a session isn't evidence; the same applies to a session nobody watched.

**The morning ritual is one file.** Read the newest desk report — one sentence of
business progress, ① done with evidence, ② needs you, ③ risks in the next 7 days —
answer the queued questions, and go. Everything else (columns, ledger, evidence,
queue) is one command away: `npx vteam-harness board`. If you find yourself reading
run logs every morning, something is wrong with the nights, not with the reporting.

## 6. Cost and usage discipline

A subscription hides the meter, which is exactly why the ledger keeps one. Every row
closes with `· tok ≈ <N>k` and DEV rows name the tier used (`ops.md` §7) — so
overnight spend is *visible* even when no invoice moves.

- **The reader is `perf_report.py`.** Run it weekly:

  ```bash
  python3 .vteam/scripts/perf_report.py --month 2026-08     # or --since 2026-08-01
  ```

- Read **Who did what (by lane)** and **Who did what (by person)** — the per-lane and
  per-person tables are where a runaway night shows up as a lane with many rows and
  little `done`. Then **Routing & accounting flags** (frontier without an escalation
  trail, utility on DEV work, unrecorded tiers), **Model usage**, **Monthly trend**,
  and the **Rough cost band** — labelled an estimate in the report itself, and it
  stays an estimate.
- The weekly read has one job: catch the trend before the plan does. Tokens per
  ticket rising with no change in ticket size means review rounds are multiplying —
  a process finding for the 14-day framework review (`ops.md` §6), argued from the
  report, never from vibes.
- Subscription-specific: if shifts routinely end early on a spent window, you are
  scheduling more work than the plan allows. Fix it by scheduling *fewer, better*
  shifts or narrowing scope — not by adding parallel sessions.

## 7. What can go wrong

| Failure | What actually happens | The designed answer |
|---|---|---|
| Usage window exhausted mid-ticket | the session stops; the ticket stays In Progress under its claim | claim TTL + the PM recovery lane reclaim it next shift (`raci.md` §2); `npx vteam-harness resume <KEY>` prints the furthest proven stage and the next move. Nothing to repair by hand |
| Network down / auth expired / credential refresh needed | the shift fails **loud** — non-zero exit in `launchctl print` / `journalctl`, and no ledger row for that hour | the next timer retries; the board and the missing run log show the gap. Subscription auth that needs an interactive re-login is an owner action — a scheduler cannot answer a login prompt |
| Two sessions on one repo | duplicate claims, competing branches, a morning spent on cleanup | the lock (§3, §4). Detected duplication is *reported*, never auto-deleted (`ops.md` §1) |
| Runaway loop / a shift that won't end | tokens burn with nothing reaching `done` | `team.md` loop guards — one attempt per item, `n=N`, the hard ceiling of 12, stop on a zero-progress sweep — plus the scheduler's own timeout (§3) |
| Machine asleep at the tick | launchd/systemd run the missed tick late; plain cron skips it | the keep-awake recipes in §4; `Persistent=true` / launchd's wake behaviour. A closed laptop lid still wins over all of it |
| Permission prompt in an unattended run | the run hangs until the timeout | decide the permission posture before scheduling (§3); fail fast rather than sit at a prompt |
| Hooks not installed in this clone (`core.hooksPath`) | the fence becomes prose, and prose gets skipped | every team session verifies the hook wiring at start (`ops.md` §5); `doctor` reports it |
| Silent success that isn't | a green night with no evidence and no ledger rows | that is not a green night. Gates go red on it, and a shift with no ledger row did no work |
